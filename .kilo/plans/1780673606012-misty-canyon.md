# Streamlit UI Cloud Deployment Strategy

## Goal

Deploy the Streamlit dashboard as a separate container so reviewers can interact with a complete product (not just APIs).

## Decision: Option B — Separate Container

**Rationale:** Clean separation of concerns, easy to swap UI tech later (React/Vue/HTMX), independent scaling, and follows the existing microservice pattern. The cost delta (~$15-30/month Fargate 256MB) is negligible for the operational benefits.

## Implementation

### Container Setup
- `services/dashboard/Dockerfile` — multi-stage build, copies `streamlit_app.py` + `libs/`, runs on port 8501
- `docker-compose.yml` — `dashboard` service depends on `ingestor`, sets `INGESTOR_URL=http://ingestor:8000`
- Nginx upstream `dashboard:8501` + `/dashboard/` location with WebSocket upgrade headers

### Key Changes
- Removed embedded approach: no Streamlit in ingestor container, no `ui.py` router
- `streamlit_app.py` reads `INGESTOR_URL` from env (default `http://localhost:8000`)
- Dashboard is swapable: replace `services/dashboard/Dockerfile` CMD to serve React/Vue/HTMX build without touching nginx or ingestor

### Files Modified
- `services/dashboard/Dockerfile` — new
- `docker-compose.yml` — added `dashboard` service
- `docker-compose.prod-like.yml` — added dashboard resource constraints
- `infra/nginx/nginx.conf` — enabled `/dashboard/` upstream + location
- `docs/deployment/aws-ecs.md` — documented embedded Streamlit Dashboard section
